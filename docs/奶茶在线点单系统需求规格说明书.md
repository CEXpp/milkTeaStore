# 1 引言

<a id="_Toc100001"></a>

## 1.1 项目背景与定位

本系统服务于一家实体奶茶门店的数字化点单与营业管理。顾客通过扫描店内微信小程序码完成自助点单与支付，商家通过 Web 端完成商品管理、柜台人工点单与账台统计；系统同时内置 AI 语音点单能力，顾客可直接对智能体说出需求即可完成下单。

**项目采用两阶段定位：**第一阶段为练手验证期，以个人主体小程序体验版 + 本机部署 + 内网穿透运行，支付使用纯 Mock 模拟；第二阶段为真实门店运营期，升级为个体工商户主体小程序 + 云服务器正式发布 + 微信支付。本文档覆盖两阶段的完整功能需求，两阶段的差异在第 12 章升级路线中逐项标明。

需要特别说明的背景事实：微信支付已向个人开放收款能力（小微商户通道），但个人主体小程序无法通过微信认证，因而无法在小程序内调起微信支付。这一制度约束决定了练手期与真店期的支付实现必然不同，系统通过支付策略接口隔离这一差异（见 6.4 节）。

<a id="_Toc100002"></a>

## 1.2 文档目的与适用读者

本文档是奶茶在线点单系统的需求基线（唯一事实来源），经三轮需求对齐后由需求方签收。后续的技术设计文档、实施计划、交接指令均以本文档为出发点；执行期间若发现设计与现实冲突，必须先修改本文档再放行新任务。

适用读者：需求方（门店经营者 / 项目发起人）、后续技术设计与实施的执行人员或执行 AI，以及参与验收的相关人员。阅读本文档无需具备 Java 或前端开发背景，关键技术术语在 1.3 节给出解释。

<a id="_Toc100003"></a>

## 1.3 术语与解释

本文档面向非资深技术读者，关键术语约定如下：

表 1-1 术语对照表

| 术语 | 解释 |
|---|---|
| 取餐制 | 顾客下单支付后在卖台前自行取餐的模式，无桌号、无送餐。店内张贴的小程序码仅作为入口，不携带桌号信息 |
| 规格 / SKU | 同一杯饮品的可选属性组合：杯型、温度、甜度单选，加料多选。本文档中 SKU 指单件订单项的完整选择 |
| 取餐码 | 支付成功后分配给订单的当日流水号，作为取餐凭证，每日从 001 重新计数 |
| Mock 支付 | 模拟支付：用户点击支付后系统直接标记支付成功，不产生真实资金流动，仅用于练手期 |
| openid | 微信赋予每个小程序用户的匿名唯一标识，系统用它识别顾客，不需手机号 |
| 静默登录 | 仓微信 wx.login 静默换取 openid 完成登录，顾客无感知、无弹窗 |
| JWT | JSON Web Token，一种服务端签发的令牌，商家端登录后携带令牌访问接口，避免每次重复登录 |
| uni-app | 基于 Vue 语法的跨端开发框架，编译产出微信小程序等多端产品，本项目仅使用其微信小程序输出 |
| LangChain4j | Java 生态中主流的 AI 应用开发框架，提供大模型对接、工具调用、会话记忆等能力 |
| 工具调用 | 大模型根据对话内容决定调用后端预置的能力函数（如查菜单、生成草稿单），用结构化参数执行真实操作 |
| MCP | Model Context Protocol，把业务能力包装成标准协议服务供 AI 调用的规范。本项目练手期不启用，仅预留升级接口 |
| 体验版 | 微信小程序未正式发布前的可扫码试用版本，仅限特定用户使用，练手期的发布形态 |
| 内网穿透 | 把本机服务暴露为公网 HTTPS 地址的临时通道（如 cpolar），供体验版小程序访问 |
| 个人主体 / 个体工商户 | 小程序注册主体类型。个人主体无法微信认证、不能接入微信支付；个体工商户持营业执照，可认证可接入微信支付 |
| 价格快照 | 下单时把商品名称、规格选择、单价实时存入订单，之后商家改价不影响历史订单与统计 |

# 2 系统总体描述

<a id="_Toc100006"></a>

## 2.1 系统定位与边界

本系统是单门店奶茶点单系统，由一个后端服务与两个前端组成：顾客使用微信小程序（扫码点单、AI 点单），商家使用 Web 管理端（订单看板、人工点单、商品管理、账台统计）。三个订单渠道（小程序、AI 智能体、柜台人工）最终汇入同一套订单状态机、取餐码流水与账台统计。

系统边界内不区分客座区域（无桌号概念），不涉及会员与营销体系，不做库存数量管理（商品仅有上下架状态）。明确不做的事项清单见第 11 章。

<a id="_Toc100007"></a>

## 2.2 用户角色

表 2-1 用户角色

| 角色 | 使用端 | 身份识别 | 核心场景 |
|---|---|---|---|
| 顾客 | 微信小程序（uni-app） | openid 静默登录 | 扫码浏览菜单、选规格、加购、支付、看取餐码与订单状态；或对 AI 智能体说话点单 |
| 商家 | Web 商家端（Vue 3 + Element Plus） | 单账号账密登录（JWT） | 订单看板操作、柜台人工点单、商品上下架、账台统计、暂停接单开关 |

商家端为单账号设计（店长账号柜台共用），不做角色权限区分；操作日志不区分操作人。

<a id="_Toc100008"></a>

## 2.3 系统架构总览

后端为 Spring Boot 单体架构，按业务领域分包（product / order / payment / statistics / ai / user / shop），为后期可能的微服务化预留拆分边界。微服务预留采用接口层预留而非协议层预留：领域之间不直接跨包访问数据表，公共能力以接口暴露；将来若拆分微服务，在接口上加协议壳（HTTP 或 MCP）即可平滑迁移，业务代码不动。

AI 智能体模块内嵌于后端（ai 领域包），基于 LangChain4j 接入大模型，点单能力以本地工具方式直连商品与订单模块（详见第 5 章）。支付模块采用策略接口设计，Mock 与未来微信支付为可替换实现（详见 6.4 节）。

<a id="_Toc100009"></a>

## 2.4 核心业务流程

<a id="_Toc100010"></a>

### 2.4.1 流程 A：小程序扫码点单

顾客扫店内小程序码 → 静默登录 → 浏览菜单（分类导航） → 选择商品与规格（杯型 / 温度 / 甜度 / 加料） → 加入购物车 → 结算下单 → Mock 支付 → 获取取餐码 → 跟踪订单状态（待制作 → 制作中 → 请取餐） → 到柜台出示取餐码取餐。支付后 15 分钟内未完成的待支付订单自动关闭。

<a id="_Toc100011"></a>

### 2.4.2 流程 B：柜台人工点单

商家登录 Web 端 → 进入人工点单界面（与顾客端同款规格选择） → 确认收款（练手期直接标记已收款；真店期为现金或当面扫码收款后点击已收款） → 系统生成已支付订单并分配取餐码 → 订单进入制作队列与小程序订单同板管理。柜台单不关联顾客身份，以渠道标记区分。

<a id="_Toc100012"></a>

### 2.4.3 流程 C：AI 语音点单

顾客进入 AI 点单页 → 对输入框说话（输入法语音转文字或手打），如“来两杯珍珠奶茶少冰半糖” → 后端调用大模型理解意图、匹配菜单 → 返回商品卡片（可多件、可删改、显示合计） → 顾客点击立即支付（快捷直付，不经购物车） → Mock 支付成功 → 汇入流程 A 的取餐码与状态跟踪。模糊订单时 AI 主动追问推荐（详见 5.2 节）。

<a id="_Toc100013"></a>

# 3 顾客端功能需求（微信小程序）

顾客端基于 uni-app（Vue 3 语法）开发，编译产出微信小程序。页面结构为底部三个 Tab：菜单（首页，购物车为浮动入口）、AI 点单、订单。

<a id="_Toc100014"></a>

## 3.1 扫码进入与登录

- 扫描店内张贴的小程序码进入小程序，码不携带任何参数（无桌号语义，全店唯一）。
- 首次进入自动调用 wx.login 静默登录，后端以 openid 识别顾客；不强制获取手机号、不弹任何授权窗口。
- 存在进行中订单时重新扫码进入，首页提示恢复进行中订单（跳转 3.6 进行中订单页）。

<a id="_Toc100015"></a>

## 3.2 菜单浏览

- 按商家设置的分类展示商品（分类导航 + 商品卡片列表）；仅展示上架商品，下架商品不可见。
- 商品卡片展示图片、名称、基础价、销售中描述；点击进入商品详情。
- 商家开启暂停接单后，菜单页显示“暂停营业”提示，禁止下单；已下单订单不受影响，照常走完流程。

<a id="_Toc100016"></a>

## 3.3 商品详情与规格选择

商品详情页展示完整信息与规格选择器。规格选择器的形态由全局规格组配置驱动（见 4.4 节商家端规格管理）：

表 3-1 规格类型与选择规则

| 规格组 | 选择方式 | 是否计价 | 典型取值 |
|---|---|---|---|
| 杯型 | 单选、必选 | 计价（价差） | 中杯 +0 元 / 大杯 +3 元 |
| 温度 | 单选、必选 | 不计价 | 热 / 常温 / 少冰 / 去冰 |
| 甜度 | 单选、必选 | 不计价 | 全糖 / 七分 / 五分 / 三分 / 不加糖 |
| 加料 | 多选、可不选 | 计价（按件） | 珍珠 +2 元 / 椰果 +2 元 / 布苔 +3 元 |

- 实时计算当前选择的单件价格：单价 = 基础价 + 杯型价差 + 已选加料价合计，选择器上方同步显示。
- 支持可选口味备注输入框（如“少放冰”），随订单一并提交，限 50 字。
- 确认加入购物车；同一商品同一规格组合合并为一条购物车记录（数量可调）。

<a id="_Toc100017"></a>

## 3.4 购物车

- 首页浮动入口（徽标展示商品种类数与合计金额），点击展开购物车抽屉或页面。
- 购物车内可增减数量、删除单条、修改口味备注；合计金额实时刷新。
- 点击结算进入订单确认页：展示商品明细、合计金额，确认后生成待支付订单并进入支付环节。

<a id="_Toc100018"></a>

## 3.5 下单与支付

- 下单即创建待支付订单（状态“待支付”），并对商品名称、规格选择、单价做价格快照；此时尚未分配取餐码。
- 点击支付弹出“模拟支付”确认框（展示金额），确认后支付立即成功（练手期 Mock 实现），订单转为“已支付”并分配取餐码，跳转进行中订单页。支付页面流保留完整的交互形态，真店期替换微信支付实现时前端页面流不变。
- 待支付订单 15 分钟未支付自动关闭（见 6.1 节），关闭前顾客取消支付意图即作徟。

<a id="_Toc100019"></a>

## 3.6 进行中订单页

- 支付成功后跳转至本页：大号取餐码、订单明细、当前状态。
- 状态实时可见：已支付（排队制作）→ 制作中 → 请取餐（已完成），状态变化时页面可感知更新（实时机制的技术选型如轮询或 WebSocket 由技术设计文档确定）。
- 中途退出小程序后重新进入，通过订单 Tab 或扫码提示恢复本页。

<a id="_Toc100020"></a>

## 3.7 历史订单

- 订单 Tab 分两段：进行中订单（含待支付）置顶展示；历史订单列表分页展示。
- 历史订单展示状态、金额、商品概要、下单时间；只读（无再支付、无取消入口）。
- 数据永久保留，仅展示当前 openid 名下的订单。

<a id="_Toc100021"></a>

## 3.8 取消与售后约定

顾客端不提供自助取消功能：待支付订单不支付自然关闭；已支付未开始制作的订单如需退款，由顾客告知店员后由商家端执行作废并线下退款（见 4.2 节）。此约定为防止恶意下单取消的最简实践。

<a id="_Toc100022"></a>

# 4 商家端功能需求（Web 管理端）

商家端基于 Vue 3 + Element Plus 开发，部署为台式或笔记本浏览器访问，适合柜台操作。为单账号系统，无多账号注册入口，账号由管理员在系统初始化时写入数据库。

<a id="_Toc100023"></a>

## 4.1 登录与会话

- 账号密码登录；登录成功后签发 JWT 令牌，后续请求携带令牌；令牌过期后跳转登录页。
- 密码连续错误 5 次锁定 10 分钟（防暴力尝试）；密码以哈希存储，不明文落盘。

<a id="_Toc100024"></a>

## 4.2 订单看板

订单看板是商家端首页与四态状态机的操作承载页，工作态主界面常驻此页：

- 区块一（待处理）：已支付待制作队列，按支付时间升序；每单展示取餐码、商品概要、金额、渠道标签（小程序 / AI / 柜台）。
- 区块二（制作中）：已开始制作的订单，同款信息。
- 新单到达时声音提醒 + 列表项高亮；看板数据自动刷新（刷新机制进技术设计文档）。
- 单笔操作：开始制作（已支付 → 制作中）；出餐（制作中 → 已完成）；作废（仅限已支付且未开始制作，需填写原因，订单转“已作废”并记录退款额）。
- 历史订单查询：按日期 / 状态 / 渠道 / 取餐码筛选，可查看订单全部明细（含规格快照与备注）。

<a id="_Toc100025"></a>

## 4.3 人工点单（柜台）

- 商家在 POS 页面以与顾客端同款的规格选择器选择商品与数量，可填写口味备注。
- 确认收款即生成“已支付”订单（练手期直接确认；真店期对应现金 / 当面扫码收款后点击确认），同时分配取餐码，可回执打印或展示取餐码小票。
- 柜台单不关联顾客身份，渠道标记为“柜台”；价格同样做快照。

<a id="_Toc100026"></a>

## 4.4 商品管理

- 商品增删改查：名称、基础价、描述、图片上传（本地磁盘存储，真店期可迁移 OSS）、所属分类、上下架开关。
- 分类管理：增删改、拖拽排序；小程序菜单按排序展示。
- 全局规格组管理：维护杯型 / 温度 / 甜度规格项与价差、加料项与加价；商品级可配置本品适用哪些规格组（如热饮不显示冰度选项）。
- 价格变更仅影响之后的新订单；历史订单持快照价，统计口径不变（见 6.3 节）。

<a id="_Toc100027"></a>

## 4.5 账台统计

- 今日概览：今日营业额、今日订单数、售出杯数、今日退款额；并按渠道（小程序 / AI / 柜台）分列展示订单数与金额占比。
- 近 7 日趋势：每日营业额与订单数折线 / 柱状展示。
- 商品销量排行：按件数排序，含规格组合明细（如珍珠奶茶-大杯-少冰卖了多少杯），可切换今日 / 近 7 日维度。
- 订单流水明细：按日查询订单清单，含异常单（超时关闭 / 作废）标记与退款额列。
- 统计口径严格按 6.5 节执行，任何报表数字与订单明细可交叉核对。

<a id="_Toc100028"></a>

## 4.6 暂停接单

- 商家端首页常驻开关：开启后顾客端全渠道禁止新下单（显示“暂停营业”）；关闭后恢复。
- 开关状态仅影响新订单：已下单（含待支付）的订单照常处理。

<a id="_Toc100029"></a>

# 5 AI 点单智能体模块

<a id="_Toc100030"></a>

## 5.1 模块定位与边界

AI 点单是小程序端专属的对话式点单入口，商家端不提供任何 AI 功能。能力边界：只做点单（含模糊推荐、规格追问、多商品一次性下单）；不查订单状态、不接闲聊、不接商品外话题（范围外话题礼貌拉回点单）。语音输入不自研 ASR，依靠手机输入法的语音转文字能力（顾客在微信键盘按麦克风说话转文字后发送），输入框同时支持手打。

架构形态：后端 ai 领域包内嵌基于 LangChain4j 的智能体服务，大模型按 OpenAI 兼容协议接入（配置化三件套：base_url / api_key / model，默认 GLM 免费档模型起步）。点单能力以本地工具方式（工具调用）直连商品与订单模块；MCP 协议壳为可选升级项，需要对外部 AI 客户端开放时再加装（工具代码不变）。

<a id="_Toc100031"></a>

## 5.2 交互流程与交付形态

- 聊天式界面：冷启动显示欢迎语与示例指令（如“试试说：来杯珍珠奶茶少冰半糖”）；对话气泡 + 底部输入框。
- 购物助手级理解能力：明确指令直接解析；模糊请求（“想喝奶茶”）主动推荐菜单候选；规格缺失时追问（“要大杯还是中杯？”）；支持一句话多商品多数量（“两杯珍珠奶茶少冰，再来一杯热柠檬茶”）；支持追加修改（“算了不要椰果了”时更新草稿单）。
- 交付形态为快捷直付：AI 解析完成后返回商品卡片（可多件、每件可调数量、可删除、显示合计金额），顾客点击立即支付直接生成正式订单进入支付流程，全程不经购物车；手动浏览点单路径（菜单 + 购物车）保留不变。
- 快捷直付生成的订单与流程 A 订单同构同构造，仅渠道标记为“AI”；同样做价格快照、分配取餐码、进入四态状态机与统计。

<a id="_Toc100032"></a>

## 5.3 工具调用与约束三原则

用户所述“约束好”落地为三条硬规则，保证 AI 不可能绕过商品与价格体系退单：

- 原则一（真实商品）：AI 只能下单工具查询返回的真实商品 ID，无法编造菜单上不存在的商品；规格与加料同理。
- 原则二（价格后算）：价格一律由后端计算，AI 只传递结构化的规格选择结果，无权定价、无权改价。
- 原则三（实时校验）：创建订单前实时校验商品上架状态与规格有效性，下架商品即使 AI 已答应也拦截并提示。

*工具清单（如菜单搜索、草稿单生成的具体签名与参数）属技术设计范畴，本文档仅约定上述能力与规则。*

<a id="_Toc100033"></a>

## 5.4 会话管理

- 会话绱定小程序 openid 与小程序会话；保留最近若干轮对话供模型理解上下文（具体轮数与超时时长在技术设计文档确定），超时自动清空。
- 草稿单（待支付的商品卡片内容）保存在会话中，顾客可继续追加修改；支付成功后草稿单转正式订单并清除。

<a id="_Toc100034"></a>

## 5.5 降级与异常处理

- 后端 AI 服务不可用（模型接口超时 / 欠费 / 断网）时，AI 点单页显示“AI 助手休息中”，引导顾客使用菜单手动点单；其余功能不受影响。
- 模型单次响应超过 10 秒视为超时，给出重试提示；超时不阻断手动点单路径。
- 理解失败或匹配不到商品时，AI 以文字形式说明并给出候选；错误不会直达订单（卡片可删改 + 支付前确认两道关）。

<a id="_Toc100035"></a>

# 6 业务规则

<a id="_Toc100036"></a>

## 6.1 订单状态机

订单全生命周期采用六状态状态机（四个主状态 + 两个终止形异常状态），所有渠道的订单共用同一台状态机：

表 6-1 订单状态迁移表

| 当前状态 | 触发事件 | 动作 | 目标状态 | 顾客端可见 |
|---|---|---|---|---|
| 待支付 | 顾客完成支付（Mock 确认） | 分配取餐码、记录支付时间 | 已支付 | 支付成功跳转取餐码页 |
| 待支付 | 15 分钟未支付 | 自动关闭 | 已关闭（超时） | 历史订单可见 |
| 已支付 | 商家点击开始制作 | 记录操作与时间 | 制作中 | 显示“制作中” |
| 已支付 | 商家作废（填原因） | 记录作废与退款额、线下退款 | 已作废 | 显示“订单已取消，请联系店员” |
| 制作中 | 商家点击出餐 | 记录出餐时间 | 已完成 | 显示“请取餐” + 取餐码 |
| 已完成 | — | 终态，不可再变更 | — | 历史订单可见 |

约束补充：已关闭与已作废为终止状态，不允许任何后续迁移；已完成为成功终态；仅“已支付”状态允许商家作废且只能在未开始制作时执行；制作中与已完成不可作废不可退款。状态迁移全部由后端校验执行，前端只展示不写入。

<a id="_Toc100037"></a>

## 6.2 取餐码规则

- 取餐码为当日三位十进制流水号（从 001 起），三个渠道共用同一条流水；每日 00:00 重置为 001。
- 取餐码在订单进入“已支付”时分配（而非创单时），避免超时单占用号码；当日内唯一，作废单的号码不回收。
- 商家端看板与人工点单小票展示取餐码；订单单号（系统流水）与取餐码并行存在，单号供查询溯源。

<a id="_Toc100038"></a>

## 6.3 价格规则与快照

- 单件价 = 商品基础价 + 杯型价差 + 已选加料价合计；订单金额 = Σ（单件价 × 数量）。金额以分为单位存储，避免浮点误差。
- 创建订单时对每个订单项做快照（商品名、规格选择明文、单价）；任何价格与规格配置的事后变更不影响已存在订单与统计。
- 创单时后端按快照规则重算金额，不信任前端传入的金额。

<a id="_Toc100039"></a>

## 6.4 支付策略

- 支付能力定义为策略接口（PaymentProvider），练手期激活 Mock 实现：确认即成功、立即分配取餐码。
- 订单预留 pay_channel（支付渠道）与 transaction_id（交易凭证）字段；柜台人工单的渠道为“柜台收款”。
- 真店期新增微信支付实现并以配置切换，前端页面流与订单状态机均不变（见第 12 章）。

<a id="_Toc100040"></a>

## 6.5 统计口径

表 6-2 账台统计口径定义

| 指标 | 口径定义 |
|---|---|
| 营业额 | 按支付完成时间归属当日；已支付及以后状态订单的实付总额，作废订单以退款额单列扣减；超时关闭单不计入 |
| 订单数 | 当日进入过“已支付”及以后状态的订单数（含作废，不含超时关闭） |
| 售出杯数 | 主饮品件数（加料、规格不另计） |
| 退款额 | 当日作废订单的实付金额合计，单独列示不与营业额混算 |
| 渠道分布 | 按订单 source 维度（小程序 / AI / 柜台）统计订单数与金额 |
| 趋势与排行 | 近 7 日逐日营业额与订单数；商品与规格组合按件数排序，可切换今日 / 近 7 日 |

# 9 非功能需求

<a id="_Toc100044"></a>

## 9.1 性能

- 单店量级假设：日单 200–500 单，午晚高峰并发用户不超过 20；不做分布式与高并发设计。
- 常规页面接口响应 95 分位不超过 1 秒；AI 对话响应 95 分位不超过 10 秒（超时按 5.5 节处理）。
- 商家看板新单提醒延迟不超过 5 秒（刷新机制进技术设计文档）。

<a id="_Toc100045"></a>

## 9.2 安全

- 商家端接口全部 JWT 鉴权；顾客订单接口校验 openid 与订单归属关系（不可跨用户读取）。
- 图片上传限制类型（jpg / png / webp）与大小（单张 ≤ 2MB）；所有入参服务端校验。
- AI 安全：系统提示词锁定点单职责；工具白名单且返回结果后端复核（三原则）；对提示词注入类攻击的主要防线是上述硬规则而非提示词本身。
- Mock 支付仅允许在练手配置下启用，真店配置不启用（配置项校验）。

<a id="_Toc100046"></a>

## 9.3 可用性与降级

- AI 服务不可用不影响手动点单主链路（按 5.5 节降级）。
- 练手期后端单点部署于开发本机，接受单点故障；真店期迁移云服务器后要求服务可用性 99.5% 以上。
- 建议每日自动备份数据库（保留近 30 天），备份脚本由实施计划落地。

<a id="_Toc100047"></a>

## 9.4 部署形态

- 练手期：后端运行于开发本机，通过内网穿透工具暴露公网 HTTPS 地址；小程序以体验版发布（个人主体），手机真扫码验证全流程。
- 真店期：云服务器 + 已备案 HTTPS 域名 + 小程序正式提审发布（个体工商户主体）（见第 12 章）。

<a id="_Toc100048"></a>

## 9.5 数据保留

- 订单与统计数据永久保留；AI 会话消息保留 90 天（排查用）后归档或清理。
- 商品图片本地磁盘存储；删除商品时图片文件保留（供历史订单概要使用的快照不包含图片，无悬挂引用）。

| 外卖配送 | 超出堂食范围 | 不计划 |
| 库存数量管理 / 缺货预警 | 上下架已覆盖售罄场景 | 原料损耗管理另立项目 |
| 叫号屏 / 取餐大屏 | 顾客端自查状态与取餐码已覆盖 | 真店期视需求另评 |

| 多语言 / 英文界面 | 单店中文语境 | 不计划 |

# 13 验收用例

以下用例为需求基线的验收标准，执行方不得自行替换或削减；每条均以真机体验版扫码为验证环境（特别注明者除外）。前置条件未注明时默认为商家已录入珍珠奶茶（中杯 12 元 / 大杯 +3）、上架中、优惠规则配置齐全：

**AC-01  扫码进入与静默登录**

- **前置：**后端已启动，体验版已上传。
- **步骤：**手机扫体验版二维码进入小程序。
- **预期：**直接进入菜单首页，无任何登录弹窗；分类与上架商品正确展示。

**AC-02  规格选择与计价**

- **前置：**珍珠奶茶基础价 12 元，大杯 +3，珍珠加料 +2。
- **步骤：**选择珍珠奶茶 → 大杯 / 少冰 / 五分糖 / 加珍珠一份 → 观察详情页价格。
- **预期：**单件价实时显示 17 元（12+3+2）；加入购物车后合计同步 17 元。

**AC-03  购物车结算与 Mock 支付**

- **前置：**购物车内已有两杯不同规格商品。
- **步骤：**结算 → 确认订单 → 点击支付 → 模拟支付确认。
- **预期：**弹出模拟支付确认框展示正确金额；确认后跳转取餐码页，取餐码为当日流水号，页面与后端金额一致。

**AC-04  订单四态实时流转**

- **前置：**存在一笔已支付订单，商家看板打开。
- **步骤：**商家点开始制作 → 顾客端进行中订单页观察 → 商家点出餐 → 再观察。
- **预期：**顾客端依次显示“制作中”“请取餐”；商家看板区块同步变化，制作中列表项消失。

**AC-05  待支付超时关闭**

- **前置：**创建一笔订单后不支付，等待 15 分钟（测试时可将超时时长缩短）。
- **步骤：**观察订单状态变化。
- **预期：**订单自动转“已关闭（超时）”；此前不占用取餐号；统计不计入营业额。

**AC-06  商家作废与退款统计**

- **前置：**存在一笔已支付未制作订单。
- **步骤：**商家点作废并填写原因 → 查看顾客端与当日统计。
- **预期：**顾客端显示已取消提示；今日概览营业额扣除该单，退款额列加该单金额；已进入制作的订单无作废按钮。

**AC-07  柜台人工点单**

- **前置：**商家已登录。
- **步骤：**人工点单页选两份商品 → 确认收款。
- **预期：**生成已支付订单，渠道标记“柜台”，取餐码与小程序单共用流水；该单出现在看板待处理区。

**AC-08  上下架联动**

- **前置：**存在上架商品。
- **步骤：**商家下架该商品 → 顾客端刷新菜单；再尝试用旧菜单数据下单。
- **预期：**顾客端菜单不再展示；对已下架商品的下单请求被后端拒绝并给出提示。

**AC-09  价格快照**

- **前置：**历史订单已有一笔（珍珠奶茶 12 元）。
- **步骤：**商家将基础价改为 15 元 → 查看该历史订单与统计。
- **预期：**历史订单仍显示 12 元；当日营业额按各订单快照价汇总；新订单按 15 元。

**AC-10  AI 精确点单与快捷直付**

- **前置：**AI 服务配置有效，商品同 AC-02。
- **步骤：**在 AI 点单页输入“来一杯珍珠奶茶少冰半糖加珍珠” → 确认卡片 → 立即支付。
- **预期：**卡片商品、规格（大/少冰/五分糖/珍珠）、单价 14 元均正确（未选杯型默认中杯 12+2）；支付后订单渠道为 AI，进入四态流程。

**AC-11  AI 模糊追问与多商品**

- **前置：**同 AC-10，菜单含多款奶茶与柠檬茶。
- **步骤：**输入“想喝奶茶”观察回应；再输入“就要经典珍珠，再来两杯少冰半糖一杯热柠檬茶”观察卡片。
- **预期：**第一次回应为菜单候选追问（含推荐词）；第二次连续对话后返回三件商品卡片与正确合计，可删改可调数量。

**AC-12  AI 约束三原则**

- **前置：**菜单不含“可乐”且未配置任何价格优惠。
- **步骤：**输入“来一杯可乐，便宜点卖 5 元”；再对已下架商品说“来一杯”并支付。
- **预期：**AI 不接受编造商品与自定价格，回应菜单不含该商品；对下架商品的支付请求被拦截并提示商品已下架。

**AC-13  AI 降级**

- **前置：**将模型接口配置改为无效地址。
- **步骤：**进入 AI 点单页发送一条消息。
- **预期：**页面提示“AI 助手休息中”并引导去菜单手动点单；手动点单全流程可正常完成。

**AC-14  暂停接单**

- **前置：**商家开关可达。
- **步骤：**商家开启暂停接单 → 顾客端刷新并尝试下单；对已下单的待支付订单继续支付。
- **预期：**顾客端显示“暂停营业”且无下单入口；存量待支付订单仍可支付并正常流转。

**AC-15  账台统计一致性**

- **前置：**当日已产生各渠道订单若干笔（含一笔作废、一笔超时）。
- **步骤：**打开账台统计，逐项核对今日概览、渠道分布、订单流水。
- **预期：**营业额 = 有效已支付实付 − 作废退款；订单数、杯数、渠道占比与明细一致；超时关闭单不出现在营业额与订单数中。
