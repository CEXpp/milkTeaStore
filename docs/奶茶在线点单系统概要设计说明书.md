# 2 系统总体架构

## 2.1 运行形态与系统上下文

系统服务于一家实体奶茶门店，三类外部角色经统一入口与系统交互：顾客（手机微信扫码进入小程序）、商家（电脑浏览器访问 Web 管理端）、外部服务（GLM 大模型与微信开放接口）。系统对外的唯一业务边界是 backend 服务：所有 API、商家端页面、商品图片均由其统一提供【练手期由 cpolar 公网隧道暴露；真店期换云服务器与备案域名，边界不变】。

![图片](奶茶在线点单系统概要设计说明书.assets/img01.png)
图 2-1  系统总体架构（分层视图）

## 2.2 技术选型与依据

选型原则：单店业务量级优先选生态成熟、中文资料密度高的组合，降低开发与排错成本；同时在支付与 AI 两个快速演进点预留替换缝。

| 层次 | 选型 | 选型依据 | 备选与未采纳原因 |
|---|---|---|---|
| 运行时 | JDK 25+ Spring Boot 4.x | 当前 LTS 与主流稳定版组合 | JDK 21：非必要的新潮，教程资料略少 |
| 持久层 | MyBatis-Plus + MySQL 8 + Flyway | 国内事实标准，中文排错案例最多；SQL 可控 | Spring Data JPA：复杂查询表达繁琐，中文案例少 |
| AI 框架 | LangChain4j（langchain4j-openai） | Java 主流 AI 框架，工具调用与记忆开箱即用；OpenAI 兼容协议不绑死模型厂商 | Spring AI：同样可用，生态略新；裸 SDK：样板代码多 |
| 商家端 | Vue 3 + TypeScript + Element Plus + Vite | 与 Java 后端配套的中后台标配，组件全、资料多 | React + AntD：团队无既有偏好时无增益 |
| 顾客端 | uni-app（Vue 3 语法） | 一套语法覆盖微信小程序，官方工具链完整 | 原生小程序：单端无收益多一套心智；Taro：React 系，非必要 |
| 图片存储 | MinIO（S3 协议） | 容器化部署与真店迁云 OSS 均平滑；行业标准技能 | 本地磁盘：最简但无技能沉淀与迁移路径 |
| 大模型 | GLM-4-flash（免费档） | 零成本起步，OpenAI 兼容三件套可配置切换 | 豆包等：协议兼容，改配置即可，不构成锁定 |

## 2.3 逻辑架构：领域分包

后端为单体应用，内部按业务领域划分为六个模块包加一个公共包。分包不是形式主义——它是排期分工单元、代码评审边界，也是未来微服务拆分的预制切割线：领域之间禁止跨包直访数据表，一律走对方的 Service 接口（即「接口层预留」）。

| 领域包 | 职责边界 | 对外提供（被依赖） | 依赖 |
|---|---|---|---|
| user | 商家账号、顾客 openid 身份、双 JWT 签发与校验 | 登录、身份上下文 | common |
| product | 商品 / 分类 / 规格组与选项 / 上下架 / 图片元数据 | 菜单查询、商品校验、价格计算（唯一计价入口） | common |
| order | 订单全生命周期：创建、四态状态机、超时关闭、作废、取餐码流水 | 创建订单、状态迁移、订单查询 | product（校验计价）、user（身份） |
| payment | 支付策略抽象与 Mock 实现、支付回调分发 | 发起支付 | order（状态迁移） |
| statistics | 账台统计：概览 / 趋势 / 排行 / 流水 | 统计查询 | order（读） |
| ai | 智能体会话、大模型调用、工具编排、草稿单 | AI 对话、确认下单 | product、order（工具实现） |
| common | 统一响应、全局异常、JWT 过滤器、工具类 | — | — |

*依赖方向约束：order 依赖 product 的校验与计价，ai 依赖 product 与 order 的工具接口；statistics 只读不写。禁止反向依赖与循环依赖，评审时以包依赖图为准。*

## 2.4 物理架构概述

练手期整套系统运行在一台 Windows 宿主机 + Linux 虚拟机上：三个 Docker 容器（backend / mysql / minio）由 compose 编排，cpolar 隧道将 backend 暴露到公网，供手机真机体验版访问。开发期与演示期双形态共用同一套容器化数据层。完整部署拓扑、编排文件与环境就绪清单在 LLD 部署章节给出，真店升级路径见第 8 章。

## 本章小结

- 架构决策：单体 + 领域分包 + 三容器编排，支付与 AI 预留替换缝，接口层为微服务拆分预制边界。
- 选型基线：JDK 17 / Spring Boot 3.x / MyBatis-Plus / MySQL 8 / LangChain4j / Vue 3 / uni-app / MinIO / GLM。
- 追溯：覆盖 SRS 2.3（技术形态）、SRS 10（技术约束）全部要求。

# 3 领域模块设计

本章按 2.3 节的领域划分逐域展开：每域给出职责、对外能力与关键设计决策。实现级细节（方法签名、SQL、字段）一律见 LLD 对应章节（附录 A 有映射表）。

## 3.1 user 域：双身份体系

- 职责：商家账号认证（单账号 + BCrypt 密码哈希）；顾客微信静默登录（code 换 openid）；双 JWT 体系签发——商家令牌（12 小时）与顾客令牌（7 天）在 claims 中携带角色，过滤器按路径矩阵分派。
- 决策：顾客登录不强制手机号（SRS 决策），订单归属以 openid 绑定校验，越权访问返回业务错误码。
- 决策：柜台人工单不关联顾客身份（匿名单，SRS 决策），订单来源字段区分三个渠道。

## 3.2 product 域：规格模型与唯一计价入口

- 职责：商品 CRUD 与上下架、分类管理、规格组（杯型 / 温度 / 甜度 / 加料）与规格项维护、商品图片元数据。
- 核心模型：全局规格组 + multiSelect 标志统一「单选组」与「加料多选组」；商品与规格组经关联表勾选适用关系（默认全选）——解决冰饮无热饮选项这类真实场景，同时保持录入简单。
- 关键决策：计价逻辑收敛为全系统唯一入口 calculatePrice（基础价 + 杯型价差 + 加料合计），菜单页、下单、AI 草稿、柜台点单一律复用——保证任何入口算出的价一致，这是 AI 约束「价格后端算」的机制基础。
- 关键决策：下单时对商品名、价格、规格选择做快照固化，之后改价改名不影响历史订单与统计（SRS 决策）。

## 3.3 order 域：状态机与取餐码

- 职责：订单创建（三渠道汇入）、四态状态机流转与越界拦截、15 分钟超时关闭（定时任务）、已支付未制作作废、取餐码当日流水分配、订单查询。
- 关键决策：取餐码在订单进入「已支付」时才分配，待支付超时单不浪费号码（对 SRS 的细化，已登记差异表）。
- 关键决策：取餐码与订单号共用一张按日序列表，同事务行锁递增；单店量级不引入 Redis。
- 顾客端不提供自助取消（SRS 决策），取消一律由商家作废并线下退款。

## 3.4 payment 域：策略抽象

- 职责：定义支付策略接口（发起支付 / 渠道标识 / 回调处理），Mock 实现即时成功；订单表预留渠道与流水号字段。
- 决策：支付做成接口抽象而非硬编码，真店接入微信支付时新增实现类 + 配置切换，前端支付页面流不变——这是 SRS 支付升级路径的技术兑现。

## 3.5 statistics 域：统计口径唯一化

- 职责：今日概览、近 7 日趋势、销量排行、订单流水四类查询。
- 关键决策：口径硬编码为领域常量——营业额按「支付完成时间」归属当日、退款额单列不计入营业额、杯数按主饮品件数统计、渠道维度按订单来源字段聚合。口径全部写死并集中一处，避免同一指标多处 SQL 各算各的（对账类 bug 的经典来源）。

## 3.6 ai 域：智能体编排

- 职责：会话管理（10 轮记忆 + 30 分钟过期）、系统提示词、大模型调用（LangChain4j，OpenAI 兼容三件套配置）、工具编排（查菜单 / 草稿单增改查）、顾客维度限流、降级兜底。
- 关键决策：AI 只做点单入口，不另起订单链路——草稿单确认后复用 order 域唯一创建入口；支付动作不设工具（AI 永远不能替用户付钱）。
- 约束三原则的落地机制：模型只能下单「工具查询返回的真实商品」；金额一律由 calculatePrice 生成；下单时校验上架状态。模型任何编造在名称匹配层即被拦截。
- 降级：模型调用失败返回专用错误码，前端显示「AI 助手休息中」并引导菜单点单——AI 故障不影响主流程。

## 本章小结

| 域 | 一句话职责 | 最关键的设计决策 |
|---|---|---|
| user | 双身份认证 | 双 JWT 按路径分派，柜台单匿名 |
| product | 商品与规格 | 唯一计价入口 + 下单快照 |
| order | 订单生命周期 | 状态机硬校验 + 取餐码 PAID 时分配 |
| payment | 支付抽象 | 策略接口，真店只换实现 |
| statistics | 账台统计 | 口径常量化，单点维护 |
| ai | 智能体编排 | 复用既有链路，支付无工具 |

# 4 数据架构

## 4.1 概念模型

数据库共 13 张表，围绕「商品定义」与「订单事实」两条主线组织：规格体系（spec_group / spec_option / product_spec_group）定义可选项；订单体系（orders / order_item）固化下单时刻的快照事实；会话体系（ai_session / ai_message）承载智能体草稿与对话历史。

![图片](奶茶在线点单系统概要设计说明书.assets/img02.png)
图 4-1  实体关系图（概念级）

## 4.2 实体一览

| 实体 | 主线 | 职责要点 |
|---|---|---|
| admin_user | 身份 | 商家账号（单账号），密码哈希存储 |
| customer | 身份 | 顾客 openid 映射，无手机号 |
| category | 商品定义 | 菜单分类，排序字段 |
| product | 商品定义 | 商品、基础价、上下架、图片 key |
| spec_group / spec_option | 商品定义 | 规格组（单选 / 多选）与规格项（价差） |
| product_spec_group | 商品定义 | 商品 ↔ 规格组适用关系（默认全选） |
| orders / order_item | 订单事实 | 订单主表 + 订单项（含价格与规格快照） |
| daily_seq | 订单事实 | 按日序列：订单号与取餐码分配 |
| ai_session / ai_message | 会话 | 草稿单（JSON）+ 对话消息 |
| shop_config | 配置 | 键值配置：暂停接单开关等 |

## 4.3 关键数据决策

| 决策 | 方案 | 理由 / 备选 |
|---|---|---|
| 订单项规格存储 | JSON 快照列 | 快照只读不作为查询条件；统计聚合按商品维度不依赖 JSON 内部字段。备选「规格子表」：为读取场景引入三表联查，收益为零 |
| 取餐码 / 订单号 | 按日序列表 + 行锁 | 同事务原子递增，天然按日重置；备选 UUID：无序不可读，店员与顾客无法口头核对 |
| 软删除 | 不做，状态字段代替 | 订单作废 / 商品下架均走状态；单店数据量无物理删除压力，统计需要完整历史 |
| 金额类型 | DECIMAL(10,2) + BigDecimal | 杜绝浮点误差；备选「分为单位整数」：跨层转换心智负担大于收益 |
| 图片地址 | 存对象 key 不存 URL | 内网穿透域名随重启漂移，存 URL 历史图片全部失效；访问统一走后端代理接口，换域名零影响 |

## 4.4 数据保留与容量预估

- 保留策略：订单与统计相关数据永久保留（SRS 决策）；AI 会话数据 30 分钟过期后惰性清理草稿，消息历史保留。
- 容量预估：按日均 500 单峰值估算，年订单量约 18 万行、订单项约 36 万行——远低于 MySQL 单表千万级优化阈值，无需分表。

## 本章小结

- 两条主线（商品定义 / 订单事实）+ 三条铁律（快照固化 / 序列表 / 存 key 不存 URL）。

*追溯：覆盖 SRS 7（数据需求）全部实体，并落实 SRS 6.2（取餐码规则）、6.3（价格与快照规则）。字段级 DDL 见 LLD 第 2 章。*

# 5 接口架构

## 5.1 分组与鉴权体系

API 按消费者分三组，共约 33 个端点（完整字段级契约在 LLD 第 3 章）：

| 分组 | 前缀 | 鉴权 | 消费者 |
|---|---|---|---|
| 顾客端接口 | /api/customer/\*\* | 顾客 JWT（登录 / 菜单 / 门店状态除外） | 小程序 |
| AI 接口 | /api/customer/ai/\*\* | 顾客 JWT（会话与草稿绑定顾客身份） | 小程序 AI 页 |
| 商家端接口 | /api/admin/\*\* | 商家 JWT | Web 管理端 |
| 公开资源 | /api/files/\*\* | 无鉴权（图片代理流） | 全部 |

## 5.2 统一接口规范

- 响应体：{code, message, data} 三段式；code=0 成功，业务错误码集中定义（参数错 / 状态冲突 / 归属错 / 暂停接单 / AI 降级等约 9 个），HTTP 状态码仅承载 401/403/500 三类基础设施错误。
- 分页：page 从 1 起 + size 上限 100，分页响应结构固定。
- 金额与时间：金额以两位小数字符串传输（防前端浮点）；时间统一 yyyy-MM-dd HH:mm:ss。
- 幂等：支付与下单接口以「订单状态前置校验 + 状态迁移原子 UPDATE」防重复提交，不额外引入幂等 token——单店量级下状态机校验已足够。

## 5.3 端点索引

下表为全量端点索引（供评审接口面完整性；请求响应字段见 LLD）：

| 域 | 端点（方法 路径） | 用途 |
|---|---|---|
| 身份 | POST /customer/login；POST /admin/login | 小程序登录换 token；商家登录 |
| 菜单 | GET /customer/menu；GET /customer/shop-status | 分类+商品+规格+价格；暂停营业状态 |
| 下单 | POST /customer/orders；POST /customer/orders/{id}/pay | 创建订单（待支付）；发起支付 |
| 订单 | GET /customer/orders/active；GET /customer/orders/{id}/status；GET /customer/orders（分页）；GET /customer/orders/{id} | 进行中订单；轮询专用轻量状态；历史；详情 |
| AI | POST /customer/ai/chat；POST /customer/ai/confirm-order | 对话（文本或卡片响应）；草稿确认下单 |
| 看板 | GET /admin/orders/board；POST /admin/orders/{id}/start\|complete\|void | 实时队列；状态操作 |
| 柜台 | POST /admin/counter-orders | 柜台下单（直接已支付+取餐码） |
| 商品 | GET/POST/PUT /admin/products*；PUT /admin/products/{id}/status\|spec-groups；POST /admin/upload | 商品 CRUD、上下架、适用规格、图片上传 |

| 分类 | GET/POST/PUT/DELETE /admin/categories* | 分类管理 |

| 门店 | PUT /admin/shop/pause | 暂停接单开关 |

## 本章小结

- 三组鉴权边界清晰；错误码集中；金额字符串化防精度问题；无 WebSocket——实时性由轮询方案承载（见 6.3）。

*追溯：覆盖 SRS 8（接口概览），并对 SRS 3.x / 4.x 各功能提供接口面支撑。*

# 6 关键机制设计

## 6.1 订单状态机

四主态 + 两异常态，状态迁移由静态迁移表硬校验，任何越界操作返回状态冲突错误码（防重复支付、防出餐后再作废等真实事故）：

![图片](奶茶在线点单系统概要设计说明书.assets/img03.png)
图 6-1  订单状态机

- 迁移表（当前态 × 事件 → 目标态）在 order 域集中定义，操作入口仅有三处：顾客支付、商家看板操作、定时任务。
- 状态变更一律使用条件 UPDATE（带当前态断言）落库，天然防并发双改。

## 6.2 超时关单与后台调度

- 机制：单条 @Scheduled 固定周期扫描「待支付且超时」订单，条件 UPDATE 批量关闭。
- 决策：轮询扫描而非延迟队列（Redis / MQ）——单店量级下每分钟一次的查询成本可忽略，换来的实现与运维简单度远超延迟队列；备选方案保留在风险登记（真店高并发再升级）。

## 6.3 前端实时性：轮询方案

- 顾客进行中订单页每 3 秒调用轻量状态接口（仅返回状态与取餐码，响应极小）；商家看板每 3 秒全量拉取队列。
- 决策依据：奶茶出品以分钟计，3 秒显示延迟对业务零伤害；单店并发远低于轮询成本的感知阈值。升级路径：状态查询接口的契约不变，未来接入 WebSocket / SSE 只加推送层、前端换监听方式——方案不推翻。

## 6.4 支付策略

- 接口抽象：支付发起 / 渠道标识 / 结果处理三个扩展点；【练手】Mock 实现即时成功（保留确认弹窗完整 UI 流）；【真店】新增微信支付实现（统一下单 + 回调验签），配置切换。
- 订单表预留支付渠道与流水号字段，前端支付页流不感知后端渠道差异。

## 6.5 AI 点单链路

从顾客一句话到订单落库的完整链路如下——注意模型在回路里只有「建议权」：商品必须来自工具查询结果，金额由后端计算，支付由用户手动触发：

![图片](奶茶在线点单系统概要设计说明书.assets/img04.png)
图 6-2  AI 点单时序（快捷直付链路）

- 会话与记忆：最近 10 轮对话 + 30 分钟无活动过期，均配置化；消息与草稿单持久化到数据库（服务重启不丢草稿）。
- 工具集（4 个）：查菜单、更新草稿单、查草稿单、清空草稿单——签名与提示词全文在 LLD。
- 降级与限流：模型调用异常返回专用错误码，前端展示降级横幅 + 「去菜单点单」引导；按顾客限流（每分钟 10 次）保护免费模型额度。

## 6.6 文件存储

- 链路：商家端上传（类型白名单 + 大小上限 2MB）→ 后端存 MinIO（key 按日期目录生成）→ 数据库存 key → 展示时经 /api/files/{key} 代理流转发。
- 决策：代理而非直链——内网穿透域名漂移对图片零影响（只需穿透 backend 一条隧道）；菜单图片量级小，代理无性能压力。

## 本章小结

- 五个机制共同的设计取向：用最朴素的机制（条件 UPDATE / 轮询 / 策略接口 / 名称匹配校验）覆盖全部需求，复杂度花在刀刃上（状态机硬校验、唯一计价入口、AI 约束三原则）。

*追溯：覆盖 SRS 6（业务规则）、SRS 3.5/3.6（支付与订单状态）、SRS 5（智能体）的实现机制。*

# 9 非功能设计

## 9.1 安全

| 项 | 方案 |
|---|---|
| 传输 | 【练手】隧道 HTTPS；【真店】备案域名 HTTPS |
| 认证 | 双 JWT（HS256，密钥环境变量注入）+ 路径矩阵过滤器 |
| 密码 | BCrypt 哈希；连续错 5 次锁定 10 分钟 |
| 越权 | 顾客订单接口一律校验归属；商家接口全量鉴权 |
| AI 注入 | 工具输入经名称→实体匹配（参数化查询），模型无价格字段，编造内容在匹配层拦截 |
| 上传 | 类型白名单 + 2MB 上限 |
| 密钥 | AppSecret / GLM key / JWT secret 全部环境变量，不入库不入前端 |

## 9.2 性能与容量

- 量级假设：日峰值 500 单、高峰并发连接 < 20、菜单接口 QPS < 10——单体 + 单库轻松承载，无需缓存层。
- 响应目标：业务接口 P95 < 500ms（本地与隧道网络除外）；AI 对话首包 < 5 秒（超时走降级）。
- 图片：菜单全量 < 50 张，代理流无压力；前端上传前压缩。

## 9.3 可用性与降级

| 故障 | 表现 | 降级行为 |
|---|---|---|
| GLM 不可用 / 限流 | AI 对话失败 | 专用错误码 + 前端降级横幅 + 引导菜单点单，主流程零影响 |
| MinIO 不可用 | 图片上传失败 / 菜单图裂 | 菜单文字信息不受影响，下单不受影响 |
| 微信接口故障 | 登录失败 | 静默重试一次后提示稍后再试（公开菜单仍可浏览） |
| 数据库故障 | 整体不可用 | 单点依赖，练手期接受；真店云托管 + 自动备份 |
